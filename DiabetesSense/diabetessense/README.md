# DiabetesSense

An explainable machine learning system for diabetes risk screening — built from the project
report's proposal, with a trained model, a live API, and a working web interface.

**This is an educational / research MVP, not a medical device.** It does not diagnose diabetes
and is not a substitute for professional medical advice.

---

## What's here

| Layer          | Choice                                                              |
|----------------|----------------------------------------------------------------------|
| Dataset        | UCI Pima Indians Diabetes Database (public, 768 records)            |
| Primary model  | Random Forest (scikit-learn)                                        |
| Baseline model | Logistic Regression, trained alongside for comparison                |
| Explainability | SHAP (TreeExplainer) — per-prediction feature contributions          |
| Backend        | FastAPI (Python) serving `/predict`, `/model-info`, `/health`        |
| Frontend       | React + Vite, charts via Recharts                                    |

This matches the tech stack and Random-Forest-as-primary-model decision from the original
project report (Sections 6, 10 and 13).

### Why this dataset

The report names candidate parameters including glucose, BMI, age, blood pressure, insulin,
pregnancy-related factors, and (optionally) HbA1c, and says explicitly: *"the exact final
input fields must match the selected dataset and reliable labels"* (Section 9). The Pima
Indians dataset is the most widely used **public, reliably-labelled** dataset that matches
most of those fields (it does not include HbA1c). It's a well-understood benchmark, which
makes it a good fit for an MVP — see **Extending this project** below for how to swap in a
larger/more clinical dataset later.

### Model results (on held-out test data)

| Metric    | Random Forest (primary) | Logistic Regression (baseline) |
|-----------|:------------------------:|:-------------------------------:|
| Accuracy  | 0.734                    | 0.734                           |
| Precision | 0.600                    | 0.603                           |
| Recall    | 0.722                    | 0.704                           |
| F1        | 0.656                    | 0.650                           |
| ROC-AUC   | 0.820                    | 0.813                           |

Full metrics (including confusion matrices) are written to `backend/artifacts/metrics.json`
after training, and are also served live at `GET /model-info`.

## Running it locally

### 1. Backend

```bash
cd backend
python3 -m venv .venv && source .venv/bin/activate   # optional but recommended
pip install -r requirements.txt

python train.py          # trains both models, builds the SHAP explainer, writes ./artifacts/
uvicorn api:app --reload --port 8000
```

Check it's alive: `curl http://localhost:8000/health` → `{"status":"ok"}`
Interactive API docs: http://localhost:8000/docs

### 2. Frontend

```bash
cd frontend
npm install
npm run dev
```

Open http://localhost:5173. The frontend reads the backend URL from `frontend/.env`
(`VITE_API_BASE_URL`, defaults to `http://localhost:8000`).

## API reference

### `POST /predict`

```json
{
  "pregnancies": 2,
  "glucose": 165,
  "blood_pressure": 82,
  "skin_thickness": 30,
  "insulin": 120,
  "bmi": 33.5,
  "diabetes_pedigree_function": 0.62,
  "age": 48
}
```

Returns risk label, probability, confidence, and SHAP contributions per feature, sorted by
magnitude (`top_factors` is the top 4; `all_factors` has all 8):

```json
{
  "risk_label": "HIGH",
  "risk_probability": 0.8343,
  "confidence": "high",
  "top_factors": [
    { "feature": "Glucose", "display_name": "Glucose (mg/dL)", "value": 165.0, "shap_value": 0.2206, "impact": "increases_risk" }
  ],
  "all_factors": [ /* all 8 features */ ],
  "disclaimer": "DiabetesSense is an educational/research screening tool, not a medical device. ..."
}
```

A value of `0` for glucose, blood pressure, skin thickness, insulin, or BMI is treated as
"not recorded" and median-imputed — the same rule used during training — rather than taken
literally (a real patient can't have 0 BMI).

### `GET /model-info`
Returns the full metrics object written by `train.py` (both models, dataset stats).

### `GET /health`
Basic liveness check.

## Deploying

The report calls for a Vercel-based architecture with the ML model "exposed through an
appropriate backend/API service rather than assuming the Python model runs directly inside
the Vercel frontend" (Section 14). This project follows that split:

**Frontend → Vercel**
1. Push this repo to GitHub.
2. Import it in Vercel, set the project root to `frontend/`.
3. Framework preset: Vite. Build command `npm run build`, output dir `dist`.
4. Add an environment variable `VITE_API_BASE_URL` pointing at your deployed backend URL.

**Backend → a host that runs a persistent Python process**, since Vercel's serverless
functions aren't a great fit for a scikit-learn + SHAP service. Good options:
- [Render](https://render.com) — free tier, `uvicorn api:app --host 0.0.0.0 --port $PORT`
- [Railway](https://railway.app)
- Fly.io

Before deploying the backend, run `python train.py` once (locally or in a build step) so
`backend/artifacts/` exists — the API refuses to start without it. Remember to also lock
down `allow_origins` in `api.py`'s CORS config to your actual frontend domain instead of `*`.

## Retraining / swapping the dataset

`train.py` is self-contained: point `load_data()` at a different CSV with the same
`FEATURE_NAMES`, update `FEATURE_NAMES` / `FEATURE_DISPLAY` / `ZERO_AS_MISSING` if the
columns differ, and rerun. Everything downstream (API, SHAP explainer, frontend form config
in `frontend/src/lib/fields.js`) reads from the generated artifacts and would need matching
updates if you change the feature set.

## Extending this project (from the report's Future Scope)

- Swap in a larger, more clinical dataset (e.g. one with HbA1c) for better real-world signal.
- Add hyperparameter tuning (`GridSearchCV` / `RandomizedSearchCV`) and probability calibration.
- Add the XGBoost / SVM / KNN comparison models named in the report's Section 6.2.
- Diabetes-type classification, once reliable type-specific labelled data is available.
- Model monitoring/versioning and an evaluation dashboard.
